## 七、🔴 需人工裁决的结构性残留

> ⚠️ **本节已处置（2026-09-16 晚）**：下列失真项已全部收敛完毕 —— 权威实施纪要与实测数字见
> `docs/DESIGN-garss-integration-and-optimization.md` §13，本节保留为**问题复盘**，
> §7.4 的处置建议**已执行**，不再是待办。

「228 条 feed URL 全部唯一」在**条目层**是干净的；但**实体层**留下了两类**方向相反**的失真：
一边把不同实体合成了一个渠道，一边把同一实体拆成了多个渠道。
它们不是零散脏数据，而是同一个根因（见 7.1）的两面。以下每一项都已定位到具体 id，**未自动处置**。

### 7.1 根因：主页回退值是 `originOf(feedUrl)`，只对「一站一 feed」成立

`parseGarssInfo` 只映射 `sourceId / title / xmlUrl / category / description`——**根本不读 homepage 字段**。
于是 `cleanCandidates` 必走 `resolveHomepage` 的回退分支，取 `originOf(feedUrl)`，即 **`协议://主机`，不带路径**。

实测验证：**182 个 garss 渠道，182 个主页等于 `originOf(首条源 url)`，零例外。**

这个回退值只在「一个站点只有一条 feed」时成立。遇到托管域名或同实体的多条 route 就失真：

| 情形 | 回退结果 | 后果 |
|---|---|---|
| 同实体的 feed 一个 `http://`、一个 `https://` | 两个不同的主页字符串 | **误分裂** —— 同一实体判成两个渠道 |
| 多条不同实体共用托管域名（feedburner、csdn…） | 同一个主页字符串 | **误合并风险** —— 不同实体看起来像同一渠道 |

第二层放大器：`normalizeHomepage`（实体分组的**比较键**）只做 `hostname.toLowerCase()` + 去尾斜杠，**保留协议**。
它把大小写、尾斜杠都归一化了，却单单留下协议——说明它本意就是「等价性比较键」，保留协议更像漏项而非设计：

```js
normalizeHomepage('https://rakuen.thec.me')  // → 'https://rakuen.thec.me'
normalizeHomepage('http://rakuen.thec.me')   // → 'http://rakuen.thec.me'   ← 不相等
```

（`normalizeFeedUrl` 保留协议是**有意的安全权衡**——不猜协议就不会抓错内容；
但 `normalizeHomepage` 是聚合用的比较键，两者的取舍不该共用同一套保守策略。）

### 7.2 后果 A：不同实体被合并进**同一个渠道**（2 例，均已开闸 🔴）

这是唯一**已经在用户侧生效**的一类。同一个渠道里塞进了名称互不相同的多家刊物的 feed：

| 渠道 id | 渠道名（= 首条 feed 的名字） | 主页 | 开关 | 渠道内的 feed |
|---|---|---|---|---|
| `feeds-feedburner` | 书伴 | `https://feeds.feedburner.com` | **启用** | `书伴`<br>`可能吧` |
| `feedx` | cnBeta | `https://feedx.net` | **启用** | `cnBeta`<br>`环球科学`<br>`摄影世界` |

> 检测口径：garss 渠道中「挂 >1 条 feed 且各 feed 名称互不相同」的一共有 3 个；
> 逐条核对后，其中 `blog-lilydjwg`（依云 / 依云's Blog）是**同一博客的两种 feed 命名**，属误报，已排除。

**① `feedx` —— 渠道名「cnBeta」，实际装了 3 家刊物**

`feedx.net` 是个 **feed 托管服务**，cnBeta、环球科学、摄影世界三家的 feed 都挂在这个域名下：
`/rss/cnbetatop.xml`、`/rss/huanqiukexue.xml`、`/rss/photoworld.xml`。
`originOf` 对三条都返回 `https://feedx.net` → 主页相同 → 被当成同一个渠道的 3 条 feed。
而渠道名取自**第一条** feed（`String(item.name || ...)`）→ 就叫「cnBeta」。

**后果**：前端「cnBeta」卡片会把环球科学、摄影世界的文章也混进来。归属错了，而且**这个渠道是开闸状态**。

**② `feeds-feedburner` —— 渠道名「书伴」，混入「可能吧」**

同款成因：`feeds.feedburner.com` 是 Google 的 feed 托管服务，书伴（`/bookfere`）与可能吧（`/kenengbarss`）
是两个毫不相干的站点，主页回退值都撞成 `https://feeds.feedburner.com`。**同样已开闸。**

> 📌 附带影响：这也说明「本轮开闸 60 个**渠道**」≠「60 个**实体**」。
> 就名额语义而言，`feedx` 一个渠道代表 3 个实体、`feeds-feedburner` 一个渠道代表 2 个实体，
> 即这 60 个渠道实际覆盖了 **63** 个实体。被折叠的部分不是冗余，是"一家卡片装了多家内容"。

**③ `blog.csdn.net` / `woshipm.com` —— 同站分栏目被拆开（均未开闸）**

### 7.4 建议的处置顺序

| 优先级 | 动作 | 说明 |
|---|---|---|
| **P0** | 拆开 `feedx`：cnBeta / 环球科学 / 摄影世界 各成一个渠道 | 唯一**已在线上错归属**的一例 |
| **P0** | 拆开 `feeds-feedburner`：书伴 / 可能吧 各成一个渠道 | 同上，已开闸 |
| **P0** | `rakuen-thec-2` 合并进 `rakuen-thec` | 前端会出两张同名卡片 |
| P1 | `ruanyifeng` 渠道移除或永久停用 + `notes` 说明 | 消除「同 feed 双写」隐患（当前三重保险，无实害） |
| P1 | `resolveHomepage` 回退值改为 `origin + 首个路径段` | **治本 A**：`feedx.net/rss/cnbetatop` 而非 `feedx.net` |
| P1 | `normalizeHomepage` 增加协议归一化 | **治本 B**：治分裂 |
| P2 | garss 导入时优先从 feed URL 路径推断主页 | 减少对 `originOf` 裸 host 回退的依赖 |
| P2 | `blog-csdn` / `woshipm-2` 补真实主页或标注「主页未知」 | 两条均已停用，不紧急 |

⚠️ **P1 两条必须同批**，且顺序是「先加路径、再加协议归一」：
只加协议归一化，会让 `feeds.feedburner.com` 那组从「侥幸没撞」变成「真的撞上」——按下葫芦浮起瓢。

> 相关的取舍说明：`normalizeFeedUrl` 保留协议是**有意的安全权衡**（不猜协议就不会抓错内容）；
> 但 `normalizeHomepage` 承担的是**实体聚合**职责，与「抓取安全」无关，共用一个保守策略是错配。
